**二、下载顺序**

| 优先级 | 对象 | 调度方式 |
| --- | --- | --- |
| P0 | 上传区目录、文件详情、补丁关系、链接清单 | 体积小，先保存，并持续更新 |
| P1 | 无已验证替代副本的原包、独立补丁、旧版、重传包和素材 | 各上传区轮转，尽早保护不同来源；“没有确认副本”不宣称“唯一副本” |
| P2 | 尚未映射到仓库作品的 VIPRPG 专用区文件、新发现的历史分区 | 不要求先整理出题名、作者或祭典才能下载 |
| P3 | 已确认另处完整保存的相同版本、重复发布文件 | 保留来源对应，源站首轮完成后再补；不能仅凭同名、同大小跳过 |

同级优先容易成功的小中型文件，同时保留固定的大文件时段，避免长尾一直得不到下载机会。按用户后续要求，暂时故障先对同一项有限重试，成功不计错误；真正未恢复的错误立即中断整个下载流程并保留排查资料，不跳过后继续其他文件。独立补丁与依赖包成组标记，保留每一个原始文件，不自动合并成“最终版”。

**三、最小执行结构与路径**

采用一个任务专用的调度进程、一份 SQLite 队列、一个 HTTP 下载器以及现成 BaiduPCS-Go。发现、下载、上传和回验分开排队；读取目录和下载文件共用源站节流器。队列支持重新启动、停止标记、进程锁和已完成项跳过，不为本任务重建网盘服务或接入 Nextcloud。

建议路径，仅为待执行默认值：

```text
D:\VIPRPG-Rescue\uploaderjp-202611\
  queue.sqlite
  source-pages\
  staging\<uploader>\<file_id>\<revision>\<safe-original-name>
  manifests\
  logs\
  private\pcs\

百度：/VIPRPG/uploader.jp/2026-11-rescue/
  files/<uploader>/<file_id>/<revision>/<safe-original-name>
  manifests/
  source-pages/
```

执行前用现有登录只读确认账户和百度剩余容量，确认目标目录身份；目录若已有文件先清点，不覆盖旧内容。新目录创建后记录身份。认证只留在私有本机配置中，不进入仓库、来源包、公开日志或清单。

队列最少记录：原始 URL、实际主机、上传区、文件编号、来源页面／作品编号、原始文件名、路径映射、页面显示大小、HTTP 精确大小、ETag／Last-Modified（若有）、实际下载字节数、下载与上传状态、百度路径及对象 ID、回验状态、重试次数、最后错误和发现／完成时间。错误分类至少区分限流、暂时网络故障、确认页、缺密码、文件已删除、源站不支持续传、上传失败和回验失败。

推荐状态顺序为 `discovered → listed → downloading → downloaded → uploaded → remote_metadata_checked → byte_verified`。`missing_file_locator`、`needs_password`、`needs_confirmation` 和 `retry_later` 为可恢复分支。清理暂存是单独事件，不与上传完成混为一谈。

`uploader + file_id` 用于候选归并；实际合并前核对主机别名及大小写。相同编号出现大小、更新时间或验证器变化时增加 revision，保留旧文件。保存原始日文文件名和编码信息，Windows 不允许的名称用可逆映射处理；不得让同名文件相互覆盖。

**四、下载与网络规则**

- [官方 FAQ](https://uploader.jp/faq/)要求不要同时下载多个文件。因此起步采用 **全服务同时下载 1 个文件、每文件 1 条连接**；目录请求同样低频限速。上传百度可以与源站下载并行。遇到 429／503 遵循 Retry-After 或退避，不通过换出口提高并发。
- 从详情页的真实下载表单解析 action、必要字段和临时地址，保持 cookie／Referer。不把下载详情页 URL 直接当作 ZIP 地址，不将 HTTP 200 的确认页、错误页或广告页记为成功。
- 输出先写 `.part`，确认响应类型、精确长度和文件签名与预期一致后原子改名。对源站原本发布的 HTML／TXT 等文件使用其元数据识别，不能一概拒绝 HTML 文件。
- 续传仅在响应支持且正确返回 206、Content-Range 与已有偏移相符，并能确认仍为同一版本时启用。服务器忽略 Range 返回 200 时不能追加；临时地址过期则重新解析详情。无法确认版本时保留旧断点并单独重下，避免拼接不同版本。
- ZIP 等文件可使用已有工具进行结构／CRC 检查，结果与“已保存原始字节”分开记录；密码压缩包、源站本就损坏的包不因无法测试而被删除。不开游戏、不主动查看包内具体内容、不额外计算 SHA-256。
- 日本源站及下载主机使用日本节点；Web Archive／Wayback 使用香港节点。共用 Clash 出口时按批次切换，确认前一批网络传输结束后再切换；不让两类请求误用同一切换出口。百度子进程使用专用直连 HTTPS 环境，清除继承的代理变量，保持源站下载的代理设置独立。
- 本次已观察到部分公共区会返回年龄确认页。执行器应区分正常列表与确认页，按真实表单处理可处理的确认状态；需要用户操作或未公开密码时保留明确待处理项。使用来源已公开的下载口令，不猜测或爆破。人工浏览器交互依仓库约定需另有明确授权。

**五、BaiduPCS 转存与暂存释放条件**

1. 复用现有 BaiduPCS-Go 二进制和 `PCUpload.py` 的调用经验；新建任务专用 `BAIDUPCS_GO_CONFIG_DIR`。只复用需要的登录配置，不复制正在使用的上传断点文件，不直接调用绑定 OneDrive 路径和队列的迁移 worker。
2. 与现有 OneDrive 上传错开批次，等待其正常空档，或在用户后续明确调度后切换；不终止现有进程。仅有独立配置并不能消除同账户带宽和限流竞争。
3. 初始每批上传 2 个文件、每文件 2 路，使用本机已经支持的 `--policy skip --retry 2 -l 2 -p 2`；只传显式队列中的完整文件，按目标父目录分组。先根据完整批次结果调整，不直接照搬旧迁移的 6×4 并发。
4. 对退出码、日志及远端对象逐项核对。BaiduPCS v4.0.1 可在部分文件失败时返回 0；“跳过同名文件”也不等于上传成功。若同名对象不是本队列已经回验的版本，进行回读或使用独立 revision，不覆盖。
5. 每个文件首先回查远端路径、类型、对象 ID 和精确字节数，标记为 metadata_checked。BaiduPCS 本机帮助说明分片上传后的远端 MD5 可能不准确，因此不把该 MD5 单独当作内容一致的证据，也不为本任务引入额外 SHA-256 核算。
6. 对准备释放的暂存文件，完整读取百度对象并与本地原件流式逐字节比较；通过后才标记为 byte_verified。只检查大小或抽样不能满足释放条件。验证流式进行，不另存整份回读副本。工具内部上传协议所需的校验由工具自行处理。
7. **滚动释放暂存是执行计划中的待授权策略，本次不删除文件。** 后续若允许自动清理，仅处理本任务目录内 byte_verified 的原始文件；先持久化清单和对象身份，确认解析后的绝对路径在暂存根目录内，再使用不带 `-Force` 的 `Remove-Item -LiteralPath`。认证、队列、来源页、日志、失败项和未回验文件一直保留。未获清理授权时保留暂存，容量阈值触发后暂停新下载。
8. 建议暂存初始上限 **80 GiB**，D 盘至少保留 **80 GiB** 空闲；到任一阈值暂停领取新文件，上传／回验继续，下载开始前为本文件预留空间。现有迁移如需更多空间则进一步缩小本任务额度。若选择保留全部本地副本，按清点结果另配容量。
9. 源站关闭前以保存源文件为先。回验跟不上但空间足够时，继续下载并保留暂存，把部分百度回验移到关站后；不能为追求“已完成”状态而删除唯一完整本地文件。

**六、实施时间表和检查点**

执行后的前 90 分钟是检查点，不是最长工作时限：确认入口发现数、成功下载数、上传及回验数、错误分布、暂存余量和下一阶段是否能赶上期限。后续保留每日台账；本次不创建后台监控或定时任务。

ETA 采用最近数个完整批次的有效速率，而非某一行瞬时上传速度。分别计算剩余文件数／每小时完成文件数、剩余字节／每小时完成字节数，并考虑下载、上传和回验可重叠的部分。小文件场景尤其要看文件数。未列出的分区与未知大小单列，不假装有精确总进度。

**七、完成判据与交付**

每个上传区记录：入口及分页是否遍历、声明文件数、实际列出数、唯一候选数、已下载数／字节、已上传数、仅元数据通过数、逐字节回验数、需密码／确认数、源站删除数及待重试数。只有明确范围内全部处理且每个差异有记录，才能称该批完成。

最终交付包括：按上传区／编号／版本存放的原始文件，来源页缓存，JSON／CSV 文件清单，仓库作品与远端文件对应表，失败／缺失清单，以及可恢复的 SQLite 队列快照。导出 SQLite 时使用一致性备份并检查数据库，不直接复制正在写入的主文件而遗漏 WAL。

二进制不放进 Git。规划材料和来源记录按批次保留；本任务不自动把祭典内容校对或桌面 UI 验收改成完成，也不自动推送或部署。现有 `catch/site-backup-2024/` 未跟踪内容保持原状。

**开始执行前需要明确的具体参数**

- 百度目标目录采用上述建议还是用户指定位置，以及当前账户可用容量。
- 本地下载阶段已采用建议 D 盘目录、80 GiB 暂存上限及 80 GiB 空闲底线；转存阶段如需调整再按实时容量修改。
- 是否授权在逐字节回验后滚动清理本任务暂存；未授权则只保留、不清理。
- 如何安排与当前 OneDrive 上传的时段；默认不打断旧任务。

百度目录、上传时段和滚动清理参数在后续启动转存时明确；本地下载阶段按用户已授权目标推进。新增测试代码、人工 UI／浏览器交互、本地模型翻译和子代理委托仍按 AGENTS.md 的明确授权边界处理。
